# Watch Party 功能与验收基线

本文整理 2026-08-13 至 2026-08-20 的实际联调诉求，作为当前分支的产品规格与回归审查依据。

## 1. 客户端启动与播放性能

- R1. 插件不得修改或阻塞 Emby 默认首页；删除或禁用一起看功能后，首页必须保持官方默认行为。
- R2. 插件启动不得执行会显著拖慢 macOS Emby Catalyst/WebKit 首屏的同步网络请求、全库扫描或外部 Web 服务初始化。
- R3. 一起看控制不得让官方 iOS 客户端的首帧加载明显慢于独立播放；同步命令必须避免反复重启同一个 115/小雅流。
- R4. 115/小雅的 403、5XX、6908 端口和 nginx Range/代理问题属于部署基础设施，但插件必须避免用高频重试或命令风暴放大它们。

## 2. 客户端能力与角色

- R5. master 可以使用 VidHub、Conflux、Emby Web 或官方 Emby 客户端；只要客户端可靠上报播放状态和位置，就可以成为时间轴来源。
- R6. 受控端必须检查 `SupportsRemoteControl` 和视频播放能力；不支持远程控制的客户端不得产生“命令发送成功”的假阳性。
- R7. VidHub/Conflux 等不可远程控制的 master 仍可控制官方 Emby 受控端；观众的播放/暂停不得反向控制 master 或其他参与者。
- R8. master 与观众是会话角色，不等同于用户账号；同一账号可同时存在官方 iOS、VidHub 等多个独立会话。

## 3. 房间、会话与播放实例生命周期

- R9. 参与者必须按 Emby `SessionId` 保存，不能按 `UserId` 相互覆盖；同一个物理 `SessionId` 同一时间只能归属一个房间，进入新房间必须注销旧房间，防止旧房间继续下发控制命令。
- R10. 每个会话还必须跟踪 `PlaySessionId`；旧播放实例的 Progress/Stop 不得覆盖或移除新播放实例。
- R11. 客户端快速退出、重播、换集、复用 `SessionId` 或遗漏 `PlaybackStart` 时，应能从可信的 Start/Progress 自动恢复，不要求用户退出房间重进。
- R12. 同一 Emby Web `SessionId` 并发残留多个 `PlaySessionId` 时，只允许当前实例更新 master 时间轴，旧实例不得造成进度来回跳。
- R13. inactive/Stop 清理只移除对应会话或对应播放实例，不得误删同账号的其他设备；保留的观众 Stop 会话必须进入休眠，禁止接收 PlayNow/Pause/Resume/Seek，只有该会话自己的可信 Start/Progress 才能恢复控制；master 会话离开时，应按明确规则晋升同用户的其他活跃会话或暂停房间时钟。

## 4. 位置与 seek 同步

- R14. master 人工拖动进度条时，受控端应主动跳转到 master 的最终位置，而不是依赖自然播放追赶。
- R15. 支持 seek 的 master 应使用事件驱动同步；VidHub 等稀疏上报客户端可以使用报告驱动校准，但旧值不得反向覆盖 master。
- R16. 正常播放漂移应有容忍区间，约 2 秒内不 seek；周期校准只作为安全网，不能每轮都让进度条卡顿跳跃。
- R17. Web seek 期间出现的无位置事件、约 0–1 秒的流重载假值和最终目标值必须合并，受控端只执行稳定的最终 seek。
- R18. 受控端刚开始播放或重新加入时，必须立即跟随当前 master；新 `PlaySessionId` 不得继承上一段视频的 seek 冷却期。
- R19. seek 命令需要确认、冷却和失败恢复；冷却用于避免 115 流反复重载，但不能吞掉换集或重新播放后的首次同步。

## 5. 播放、暂停与单向控制

- R20. master 的播放/暂停必须同步到所有可控参与者。
- R21. 房间播放状态固定由 master 单向控制；观众的本地播放/暂停不得广播到 master 或其他参与者。
- R22. 观众播放状态偏离 master 时，只能把该观众恢复到 master 的权威状态；配置模型和管理页面不得再暴露 Anyone/Host/Vote 权限模式。
- R23. 暂停发生时应主动做一次无偏移的位置同步；无位置 Pause/Unpause 必须冻结/恢复 master 投影时钟，不能每暂停一次凭空快进约 15 秒。
- R24. 远程 Pause/Unpause/Seek 产生的延迟回声不得被误判为新的用户控制事件，也不能形成控制回路。

## 6. 剧集队列与换集

- R25. 剧集房间在同一个房间内维护当前剧集与有序队列；master 手动选集或自然播完时，受控端应自动播放同一新剧集，不创建新房间。
- R26. 多次快速选集只执行最后一次有效选择；并发、重复或上一集迟到的 Stop 不得跳过剧集或清除新会话。
- R27. 受控端换集期间即使 Start 延迟、缺失或先收到 Progress，也必须保留房间成员身份并恢复同步。
- R28. 受控端误开非当前剧集时，应被重定向到房间当前剧集与 master 位置，同时避免重定向循环。

## 7. 配置页面与可理解性

- R29. 配置页面应以中文清晰解释单视频房间与剧集房间、master 用户、允许用户、等待室、同步间隔/偏移/容忍区间，以及播放状态由 master 单向控制。
- R30. 只在相关模式下显示相关字段；切换房间类型时不得保留会造成校验或保存错误的隐藏旧值。
- R31. 表单必须提供合理默认值、范围约束、错误提示、保存反馈和危险操作确认；不得依赖用户理解内部 ticks、SessionId 或客户端实现细节。
- R32. 页面应适配 macOS/iOS 常见宽度，键盘可操作，标签与输入框关联，状态/错误信息具备基本可访问性。
- R33. Emby 内嵌配置页是唯一管理与控制界面；Homepage 等外部入口只允许链接到该认证页面，不再维护第二套控制台。

## 8. 鲁棒性、可观测性与验证

- R34. 核心状态转换应从 `ServerEntryPoint` 的事件处理器中提取为可单测模块，避免一个文件同时承担会话、时间轴、换集、权限与 UI 配置职责。
- R35. 所有已发生的生产故障都必须有确定性回归测试：多会话覆盖、迟到 Stop、旧 Progress、seek 风暴、无位置暂停、观众反控隔离、换集竞态和首次加入冷却继承。
- R36. 日志应记录关键决策与能力不足，但不得对每秒旧 Progress 产生 Info 级日志洪水；错误日志必须能区分服务器已接受命令和客户端已确认执行。
- R37. 最终交付必须通过完整 .NET 测试、配置页 JavaScript 回归测试、Release 构建，以及配置页面的实际渲染与交互检查。

## 9. 管理面安全与配置一致性

- R38. Emby 内嵌 API 必须使用当前已认证的 Emby 用户身份；Ready/Start 不得相信请求体伪造的 `UserId`，用户列表仅管理员可读。
- R39. 插件不得启动独立外部 HTTP 监听器，不得保存外部控制台 API Key/管理员密码，也不得提供绕过 Emby 身份验证的元数据代理。
- R40. Homepage 等部署层入口必须直接指向 Emby 的 `watchpartyconfig` 页面，由 Emby 本身负责登录、HTTPS 与访问控制。
- R41. 升级时旧 XML 中已经退役的外部控制台字段必须可安全忽略，且不得使插件启动或配置加载失败。
- R42. 合法的数值 0、房间 master/host、白名单和等待室最低人数语义必须在内嵌页与服务端保持一致。
- R43. “在线”与“可远程控制”必须分开表达：通过当前播放代次校验且仍在持续上报的客户端应显示在线；官方 iOS 缺少活动 WebSocket 时必须显示控制连接已断开，并禁止发送控制命令，而不是误报离线或回退 Firebase。
- R44. 配置页向当前 Web Session 一键开播时不得使用可能跨页面残留的全局加载遮罩；等待状态应限制在开播按钮内，页面切换时必须释放其他全局加载状态。
- R45. Emby `QualityChange` 事件在缺少 `PlaybackStart` 时可以安全替换同一会话的当前播放代次；普通 Progress 和已退休代次仍不得接管权威时钟。
